# Notes for Gemini

You are writing code for **Gez**, a grand strategy game for Mac and iPad.
The owner does not write code. Claude reviews and tests every change you
make before it reaches `main`.

**Read these first and follow them exactly:**
1. `CLAUDE.md`: the project rules (they apply to you too).
2. `docs/HANDOFF.md`: current state, data pipelines, how CI works.
3. `docs/ROADMAP.md`: the agreed plan. Work through phases in order.
4. `docs/DESIGN.md`: how every system works, with all its numbers.

## How to work

- **Always start from the latest `main`.** Before each new branch run
  `git fetch origin && git checkout -b gemini/<topic> origin/main`, so
  changes made since your last session (docs, roadmap decisions) are
  kept. Never revert lines you did not mean to change.
- **Never push to `main`.** Make a branch named `gemini/<short-topic>`
  (for example `gemini/phase6-armies`), commit there, push it and open a
  pull request into `main`. Claude reviews and merges it.
- One topic per branch and pull request. Keep each change small enough to
  review; split big phases into steps (data, simulation, tests, UI).
- Ask the owner design or history questions as multiple-choice questions
  (2–4 options, recommended first), one topic at a time, **before** you
  build. Record their answers in `docs/DESIGN.md` and the roadmap.
- `Packages/GezCore` stays pure Swift (no SwiftUI, Metal, UIKit, AppKit,
  Combine). All randomness through `GameRandom`. Bulk data as
  struct-of-arrays. Every new system gets unit tests in
  `Packages/GezCore/Tests`.
- Data goes in `data/` as text and is turned into JSON by the generators
  in `tools/` (table in `docs/HANDOFF.md`). Commit the regenerated files.
  New JSON resources must be added to `Packages/GezCore/Package.swift`.
- Never commit `Gez.xcodeproj` (it is generated by XcodeGen).
- Never use data or art from Paradox or Creative Assembly games.
- History: invent people or facts only where history records nothing;
  list doubtful facts in `docs/HISTORY_NOTES.md`.
- Never ask for, print or commit API keys or tokens.

## In the pull request description, write

- What you changed and why, in plain language.
- Which roadmap phase and step it belongs to.
- How you tested it (which tests you added; whether you built in Xcode).
- Anything you were unsure about.

Claude will check: CI (Linux and macOS tests, app build, snapshots), the
rules above, the tests, the game balance where numbers changed, and that
the docs were updated. Expect review comments and fix them on the same
branch.
